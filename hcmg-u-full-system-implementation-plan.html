HCMG U — Full System Implementation Plan

Harris Capital Mortgage Group · hcmgloans.com/university · Integrated into existing Next.js + Supabase application

1. Guiding Architecture Decisions

What we're building on top of

The existing HCMG app is a Next.js 14 App Router project on Vercel, backed by Supabase (Postgres + Auth + Storage + RLS). Auth uses email/password with mandatory TOTP MFA enforced in middleware.ts. The existing profiles table is the single source of truth for identity and roles.

HCMG U is added as a new top-level route group /university — the same session, same login page, same Supabase project. No second credential set. No iframe. No separate domain.

Auth flow (unchanged): Visitor → /login?next=/university → password → TOTP MFA → AAL2 JWT issued → middleware validates AAL2 → server layout checks employment_status = active AND university_access = true → user lands in HCMG U.

2. Database Changes

2b. New tables — HCMG U schema

TablePurpose

Critical security rule on video_token: The uni_lessons table stores only an opaque token — never a real HeyGen share URL or storage URL. A protected API route (/api/university/video-url) exchanges the token for a short-lived signed URL after verifying the caller's access, then returns it to the client. This keeps real video addresses out of page source entirely.

3. Middleware Changes

middleware.ts additions (surgical — no existing logic touched)
  1. Add isUniversityRoute = pathname.startsWith("/university") to the route detection block.
  2. Add isUniversityRoute to isProtectedRoute so MFA (AAL2) is enforced on all /university/* paths automatically — same logic already used for /admin and /portal.
  3. Unauthenticated visitor on a university route → redirect to /login?next=/university (sanitized: only /university* internal paths are accepted as next values).
  4. Add /university/:path* and /university to the matcher config array.
  5. Sanitize next parameter: reject any value that does not start with / or that starts with // or contains a protocol (:).

The deeper authorization check (employment_status + university_access) is intentionally done in the layout server component, not middleware, to keep middleware lean and avoid extra DB calls on every route segment during navigation.

5. Authorization Model

manager✓own team only✗✗own team only✗
trainer✓✗✓✗✗✗
university_admin✓✓✓✓✓✓

The existing portal role = admin or developer implicitly grants university_admin. These are not stored separately — hasUniversityAccess() in lib/auth.ts checks both.

Dual gate on every server component: Both conditions must pass to enter HCMG U —
1. profile.is_active = true AND profile.employment_status = 'active'
2. profile.university_access = true
If either fails: show neutral "Access Denied" screen with support email. Zero course metadata shown.

6. Security Architecture

ConcernHow it's handled
Route protectionMiddleware enforces AAL2 (MFA verified). Layout server component enforces employment + university_access. Both must pass.
Former employee revocationSetting employment_status = 'inactive' OR university_access = false blocks access on next request — even if a browser session is still alive — because getCurrentProfile() re-queries the DB on every protected layout render.
Video URL exposurevideo_token stored in DB (not the real URL). /api/university/video-url verifies auth + enrollment, then returns a short-lived signed URL. Never stored in DOM or page source.
Downloadable resourcesStored in a private Supabase Storage bucket. /api/university/resource-url issues a 60-second signed URL per file per authenticated, enrolled user.
Quiz integrityCorrect answers never sent to client. /api/university/quiz scores server-side from DB, writes attempt record, triggers certificate logic.
RLSRLS enabled on all 8 new tables. Users can only SELECT their own progress rows; admins use service-role API routes for writes that span users.
SEO exclusionrobots: { index: false, follow: false } in the university layout metadata (same pattern as admin/portal). Matches existing conventions.
Audit logginguni_audit_log records: sign-in to /university, lesson started/completed, quiz attempt, certificate issued/revoked, access granted/revoked, failed access attempt, admin CRUD actions.
CSPHeyGen embed domain added to frame-src in buildCsp() in middleware. Only approved video hosts.

10. Visual Design Direction

Design tokens — extending the existing Tailwind config

The existing HCMG design system (navy #142850, orange #F37021, white, Montserrat bold) is reused wholesale. HCMG U adds a thin layer of university-specific brand expression:

  • Sidebar label reads "HCMG U" under the Orange Key logo
  • Learning path cards use HCMG navy backgrounds with orange accent progress indicators
  • Course hero banners use the navy-to-deep-navy gradient (linear-gradient(145deg, #142850, #1a3260)) already used on the login panel
  • Progress rings are SVG, orange stroke on navy background
  • Required course badge: red dot + "Required" label
  • Certificate cards: gold accent variant of the existing card shadow

No new Tailwind colors needed. Layout pattern mirrors admin/portal: fixed sidebar left, scrollable main content right, 14px mobile hamburger that collapses into a drawer.

11. Build Sequence (Implementation Order)

  1. DB migration — Add 4 profile columns + create all 8 university tables with RLS policies. Single migration file: 20260901_hcmg_university.sql. Backfill: existing admins → university_admin access; existing active LOs → learner access.
  2. TypeScript types — Add UniversityRole type + all 8 table interfaces to lib/database.types.ts. Extend Profile interface with 4 new columns.
  3. lib/auth.ts additions — hasUniversityAccess(), getUniversityRole(), isUniversityAdmin(), logUniAudit(). No changes to existing functions.
  4. middleware.ts — Add isUniversityRoute, add to isProtectedRoute, add to matcher, add next sanitization helper.
  5. API routes — All 6 routes under /api/university/. Each validates auth with getUser() + DB profile check before touching any data.
  6. University layout + access-denied screen — app/university/layout.tsx (server, dual gate) + components/university/UniversityLayoutClient.tsx + UniversitySidebar.tsx.
  7. Learner pages — Dashboard, Course, Lesson, Search, Certificates pages in order.
  8. Admin sub-layout + pages — app/university/admin/layout.tsx + all 5 admin pages.
  9. Admin components — CourseEditor, LessonEditor, AssignmentPanel, ReportTable.
  10. CSP update — Add HeyGen embed domain to frame-src in middleware buildCsp().
  11. Typecheck + lint pass — tsc --noEmit clean before calling done.

12. What Is Explicitly Not Changing

  • The existing /login page — zero modifications. HCMG U reuses it via ?next=/university.
  • The existing MFA enrollment / TOTP verification flow — unchanged.
  • The profiles RLS policies for existing columns — only additive column changes.
  • The /portal, /admin, /liftoff, or /goal-engine routes — no cross-contamination.
  • Supabase project — same project, same anon key, same service role. No second Supabase instance.
